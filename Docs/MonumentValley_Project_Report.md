# 《纪念碑谷》风格 Unity 解谜游戏项目汇报

## 一、项目背景与目标

本项目以《纪念碑谷》的核心体验为参考，目标是制作一款基于等距视角和非欧几何的 3D 解谜游戏原型。玩家通过旋转建筑或改变观察方向，让原本在 3D 空间中分离的道路，在屏幕上形成视觉连通，随后控制角色沿路前进并抵达终点。

项目经历了两个阶段：

1. **第一阶段：Python + PyOpenGL 技术验证。** 目标是验证等距投影、立方体绘制、鼠标旋转和“屏幕 2D 连通”思路是否可行。
2. **第二阶段：Unity 原型开发。** 目标是复用第一阶段的问题意识，利用 Unity 的相机、射线、动画和场景系统完成更完整的可玩原型，并打包为 Windows 版本。

项目当前已经具备两关可玩流程、角色移动、枢轴旋转、相机旋转、条件连通、按钮机关、关卡解锁、进度保存、UI 界面和 Windows 打包能力。整体仍属于课程项目原型，关卡数量和内容量有限，但核心玩法链路已经跑通。

### 2.2 总体架构

Unity 版本围绕“可行走节点图”组织玩法：

- `Walkable`：标记可行走方块，保存相邻路径、楼梯、按钮、终点和移动状态。
- `WalkGraph`：使用 BFS 查找从当前节点到目标节点的最短路径。
- `PlayerController`：负责点击选点、移动状态机、逐段移动、角色朝向和动画参数。
- `PivotController`：按 90 度步进旋转枢轴，并记录离散旋转步数。
- `CameraController`：负责正交等距视角和 90 度四向旋转。
- `GameManager`：管理与旋转角度、相机朝向相关的条件连边。
- `LevelDefinition` 和 `LevelCatalog`：保存关卡名称、场景名和关卡顺序。
- `GameSessionManager`：负责关卡加载、解锁、暂停、完成和持久化。
- `LevelUIController`：运行时生成 HUD、暂停面板、关卡选择面板和完成面板。
- `LevelValidator`：检查无效路径、终点数量、枢轴引用和条件配置。

这种结构把“场景表现”和“连通规则”分开。场景只负责放置方块，脚本负责判断哪些节点当前可以通行。

## 三、核心功能实现

### 3.1 等距视角与镜头

Unity 版本使用正交相机，保持约 35.264 度俯角和 45 度水平偏移，形成典型的等距视角。相机可以按 90 度四向旋转，旋转结束后重新计算依赖相机方向的条件路径。镜头聚焦点可以根据关卡锚点配置，不需要为每个视角重新制作场景。

### 3.2 鼠标旋转与 90 度吸附

第一阶段通过鼠标左右拖动旋转整座岛，松手后吸附到最近的 90 度。Unity 第二阶段将该思路拆分为两类控制：

- 中心枢轴和右侧枢轴负责建筑结构的 90 度步进旋转。
- 相机负责四个观察方向的旋转。

离散步进避免持续插值造成角度漂移，也让连通条件更容易稳定判断。

### 3.3 点击寻路与角色移动

玩家点击可通行方块后，系统使用 BFS 计算最短路径。`PlayerController` 使用状态机区分 `Idle`、`Moving` 和 `Locked`，移动期间拒绝重复点击。角色逐段移动到下一个节点，并同步更新当前逻辑节点，不再依赖角色悬空时的射线结果。

移动到楼梯或高度变化节点时，系统根据高度差设置动画 Blend，使角色表现更接近上台阶或下台阶。

### 3.4 非欧连通与视觉错觉

项目的核心机制是屏幕空间连通判断。对需要形成视觉错觉的节点，系统把节点“可站立点”投影到屏幕坐标，再比较两个节点在屏幕上的距离和 3D 世界距离：

- 屏幕距离足够近，说明视觉上看起来连通。
- 世界距离仍保持一定间隔，说明 3D 空间中并没有真正贴合。
- 两个条件同时满足时，脚本才开放对应移动连接。

这样，玩家看到的是一条接上的路，但场景几何本身没有被真正修改。第二关中，`l_1 (28)` 与 `p1/p2/p3` 的对齐就采用了这一逻辑。

### 3.5 条件连通与按钮机关

`GameManager` 支持两种条件：

- `ObjectAngle`：判断某个枢轴或物体的欧拉角是否满足目标角度。
- `CameraQuarterTurn`：判断相机是否转到指定四分之一方向。

满足条件后，系统开放对应路径。按钮节点支持只触发一次，并能让指定枢轴按指定方向旋转。

### 3.6 关卡流程与存档

Unity 版本包含两个关卡场景：

1. `SampleScene`：第一关，复用原有 31 个 Walkable 节点和条件图。
2. `Scene 2`：第二关，接入关卡目录与关卡选择界面。

玩家完成第一关后解锁第二关。最高解锁关卡和最后进入的关卡写入 `PlayerPrefs`，重新启动游戏后可以继续选择已解锁关卡。

### 3.7 UI 与视觉优化

UI 包含 HUD、暂停面板、关卡选择面板、完成面板和淡入淡出遮罩。界面使用深紫背景、紫粉按钮和浅色文字，与第二关的紫粉主题保持一致。HUD 精简为左上角的小面板，只保留关卡名和暂停按钮，减少对游戏画面的遮挡。

第二关视觉层增加了：

- 柔和主光和补光
- 简单阴影
- 渐变背景
- 环境颗粒层
- 关卡切换淡入淡出

颗粒层位于游戏画面之上、UI 之下，不拦截鼠标输入。

### 3.8 打包与运行

项目已配置 Windows 64 位打包脚本，包含 `SampleScene` 和 `Scene 2`。当前成品输出为 `Builds/Windows/MonumentValley.exe`。

游戏内退出方式：

- 按 `Esc` 打开暂停面板，点击 `Quit`。
- Windows 下按 `Alt + F4`。

## 四、关键难点与解决方案

| 难点 | 问题表现 | 解决方案 | 当前结果 |
| --- | --- | --- | --- |
| 顶点误判连通 | Python 版本仅凭 3D 位置判连通，顶点相邻也会被算作可走 | 明确“边相邻才算连通”，增加屏幕投影和高度差规则 | 思路迁移到 Unity 的节点图与条件系统 |
| 高度差移动 | 角色无法自然跳到高一格，楼梯表现不稳定 | 增加楼梯标记、高度差判断和动画 Blend | Unity 版本支持基本高度变化表现 |
| 非欧连通过于抽象 | 3D 断开、屏幕相接的关系难以配置 | 使用屏幕投影距离和世界距离双条件 | 第二关加入视觉对齐连接 |
| 场景数据引用脆弱 | 节点重名、重命名和缺失引用会破坏图 | 增加 `LevelValidator` 和运行时兼容适配器 | 不重写场景也能修正关键连接 |
| AI 辅助调试困难 | AI 看不到运行时画面，容易盲改 | 把需求拆成小范围修改，使用日志、投影计算和批处理验证 | 提高修改可控性 |
| UI 遮挡画面 | 顶部元素过多，按钮容易超出卡片 | HUD 精简并靠左上角，面板按钮重新居中 | 画面遮挡减少 |
| 打包并发冲突 | Unity 编辑器打开时，命令行构建无法获取项目锁 | 关闭编辑器后使用批处理构建脚本 | 成功生成 Windows 版本 |

- 枢轴旋转和相机四向旋转
- 角度条件和相机条件控制连通

### 5.2 技术成果

- BFS 最短路径寻路
- 节点图动态开关
- 离散 90 度旋转
- 屏幕空间视错觉连通

### 5.3 阶段性不足

- 关卡数量和内容量仍然有限。
- 第二关的节点命名和连接规则仍有继续整理的空间。
- 角色动画比较基础，缺少完整动作表现。
- 音效、剧情文本和更完整的新手引导尚未实现。
- 关卡编辑器仍然依赖 Unity Inspector，制作效率有限。

## 六、总结与收获

第一阶段验证了 PyOpenGL 自研路线的可行性，完成了窗口、等距相机、3D 方块、关卡读取、鼠标旋转和点击寻路等模块。项目证明“屏幕 2D 连通实现非欧效果”的思路可行，但也暴露出自研引擎在拾取、深度、高度差和调试效率上的成本。

第二阶段转向 Unity 后，项目可以集中精力处理玩法本身。当前版本已经把非欧连通、路径寻路、关卡条件和 UI 流程串成完整原型，并成功完成 Windows 打包。

主要收获包括：

- 学会把视觉错觉拆解为可计算的投影和连通条件。
- 掌握节点图、BFS、状态机和运行时 UI 的组织方式。
- 理解了离散旋转比连续角度更适合条件连通判断。
- 认识到 AI 适合执行清晰规格和局部修改，不适合代替游戏设计判断。
- 体会到场景数据维护、可复现构建和版本管理对游戏项目同样重要。
